REASONING: Every factual part of the claim checks out in the code, and this is the path that runs on the phone. The claim's causal story needs two corrections, though.

1) The grid fill is world-axis aligned with a fixed 25 cm pitch, and it really runs on device. RoomScanner takes its fill and outline materials straight from the ARPlaneManager plane prefab. Both scenes use ARToolkitPlane.prefab, whose fill material is ARToolkitPlane.mat. That material uses the "Erasmus AR Toolkit/AR Surface" shader (guid a54795e8...) with _BaseMap tiling 4. The texture is made by GridTextureFactory with one line along one edge of each tile, so you get one grid line every 1/4 m. The UVs are world XZ times the tiling. The scan meshes are built in world space: cell centres are (OriginX+x+0.5)*0.05, and the mesh root sits at the world origin with no rotation. In AR Foundation/ARCore, world X/Z comes from the phone's heading when the session started. Only Y is tied to gravity. Nothing in Runtime/Scanning estimates the room's direction or rotates the UVs (a grep for yaw/align/dominant/orthogon/simplif/douglas finds nothing relevant). The grid therefore lies at an arbitrary angle and spacing compared with the classroom tiles. The shader's own header says this is on purpose: overlapping planes share one grid. Nothing prevents it. The ARCore plane visuals (outside a scan) use the same material, so they have the same behaviour.

2) The edges come from marching squares over a 1-2-1 blurred evidence field, with no simplification or straightening. This is confirmed in SurfaceMeshBuilder L88-156 and L168-216. Each marching-squares segment becomes one 1 cm outline quad (L323-343), and the occluder walls use the same segments. There is no Douglas-Peucker pass, no snapping to room axes, and no memory of the previous outline between rebuilds (one every 0.5 s).

Correction A: the shader does not make the perspective itself wrong. The depth-test pull (shader L97-102) scales the vertex toward the camera along its view ray, so the grid lands on screen exactly where a horizontal plane at level.Height would be. The mismatch with the tiles is (a) rotation, because the session heading is arbitrary, (b) spacing, 25 cm against the real tile size, and (c) parallax from any error in level.Height. This claim explains the "does not match the tiles" part of S1, not the "sinks below the floor" part. That part is a height or depth problem somewhere else.

Correction B: the mesh builder does not create the holes and islands in S3. Those come from the evidence and from SurfaceRegionFilter (MinRegionArea 0.06 m², MaxHoleArea 0.25 m²). That value ranges from about -1.5 for a carved cell (log-odds -1.2) to about +1.8 for a confirmed cell with an ARCore plane prior. The blur mixes these uneven magnitudes, so the zero crossing depends on how strong the evidence is, not only on whether a cell is shown. Worked example: a weakly shown edge cell (+0.05) between a confirmed cell (+1.3) and a carved cell (-1.5) blurs to (1.3+0.1-1.5)/4 = -0.025, so it disappears from the fill. A hidden unknown cell (-0.3) between two confirmed cells (+1.3) blurs to (1.3-0.6+1.3)/4 = +0.5, so it gets filled in. As the log-odds change from frame to frame, the outline shifts by up to about one cell (5 cm) at each rebuild. Thin one-cell strips vanish and edges look wavy. The fill edge also lies between cell centres, so it does not match exactly the shown-cell set that the raycast uses.
CORRECTED: The fill UVs are world XZ × 4 on a texture with one line per tile, so the grid is 25 cm and aligned to the ARCore session axes, which follow the phone's heading at session start. (2) The Surface Depth pass overwrites real depth up to 0.15 m above the floor with floor depth, so the bottoms of chair legs no longer occlude the floor grid.
FIX: This is not a config fix. Changing SceneBuilder.cs:81 alone has no effect. To add real obstacle geometry on ARCore:
(1) In RoomSurfaceMap, add a 2.5D obstacle-occupancy grid, for example 5 cm columns with minimum and maximum occupied height above the floor. Fill it from the DepthScanSource points that are not up-facing and lie between floor + 0.05 m and camera height; use miss rays to clear it.
(2) Draw the occupied columns as depth-only occluders (and optionally a debug visualization), and use them to carve or clip the floor and desk levels.
(3) Optionally set `PlaneDetectionMode.Horizontal | PlaneDetectionMode.Vertical`, and teach ArcorePlanePriors and ARPlaneSurfaces to accept vertical planes as wall priors.
(4) For the chair-leg bleed, lower SurfaceDepthMaterials.PullHeight (for example to 0.03-0.05 m), or make it depend on distance.
